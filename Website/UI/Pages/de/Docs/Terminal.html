Vordergrund und Hintergrund

Der Agent entscheidet anhand der Aufgabenabhängigkeiten, wie ein Befehl gestartet wird. Benötigt der nächste Schritt unmittelbar das Ergebnis des Befehls, gibt ein normaler Vordergrundaufruf dieses direkt zurück. Können unabhängige Schritte parallel weiterlaufen, liefert ein expliziter Hintergrundstart sofort eine Task-ID zurück. Der bloße Name eines Befehls entscheidet nicht darüber, welche Startart richtig ist.

Läuft ein Vordergrundbefehl nach Ablauf der konfigurierten Wartezeit noch weiter, wechselt er als derselbe Prozess in den Hintergrund; er wird dabei nicht neu gestartet. Die Standardwartezeit ab Werk beträgt 120 Sekunden. Erkennt das Betriebssystem, dass der Prozess auf eine Tastatureingabe wartet, kann die Übergabe schon früher erfolgen. Bloße Stille ohne Ausgabe ist jedoch noch kein Beweis für eine Eingabeaufforderung.

Shell und Arbeitsverzeichnis

Jeder Aufruf startet eine frische Shell; ein cd wirkt also nicht in nachfolgende Aufrufe hinein. Das Arbeitsverzeichnis des Befehls muss für den jeweiligen Aufruf angegeben werden. Die automatische Shell-Auswahl nutzt eine auf dem Betriebssystem verfügbare unterstützte Shell; über die erweiterten Einstellungen lässt sich ein absoluter Pfad zu einer installierten Shell festlegen.

Das Befehlskästchen zeigt an, welche Shell tatsächlich ausgeführt wurde: $ für bash und zsh, PS> für PowerShell und > für die Eingabeaufforderung. Ein Wechsel der Shell ändert auch die Befehlssyntax. Shell-Befehle unterliegen dem aktuellen Berechtigungsmodus und dem freigegebenen Geltungsbereich; Terminaleinstellungen allein erteilen keine Ausführungsberechtigung und keinen Zugriff auf lokale Dienste.

Den tatsächlichen Statusbericht lesen

Running
Der Prozess läuft noch; dies ist noch kein erfolgreicher Abschluss.
Waiting for input
Das System hat erkannt, dass der Prozess auf eine Eingabe wartet. Lies die Eingabeaufforderung im Log, bevor du antwortest.
Completed / Failed
Der Prozess wurde beendet. Prüfe Exit-Code und Ausgabe; ein erfolgreicher Exit-Code bestätigt nur das, was der Befehl selbst geprüft hat.
Killed
Der Prozess wurde abgebrochen. Gehe nicht davon aus, dass bereits teilweise ausgeführte Schritte automatisch zurückgerollt wurden.
Lost
Rune kann kein reguläres Endergebnis bestätigen, etwa nachdem die Verbindung zur überwachten Laufzeitumgebung verloren ging. Dies gilt nicht als Erfolg.

Sobald ein Hintergrundprozess endet oder ein Warten auf Eingabe erkannt wird, benachrichtigt Rune den Agenten direkt mit dem vollständigen Bericht: welcher Prozess betroffen ist, wie er endete, seine PID, seine Laufzeit, der Pfad seiner Log-Datei sowie die Ausgabe, die der Agent bisher noch nicht erhalten hat. Der Agent muss nichts separat abfragen und startet denselben Befehl niemals doppelt, nur um dessen Ausgabe zu lesen; eine gekürzte oder unvollständige Erfassung wird direkt in dieser Zeile vermerkt.

Die gespeicherte Log-Datei

Jeder Hintergrundbefehl schreibt eine eigene Log-Datei auf deinem Rechner. Sie enthält die abgeschlossene Ausgabe und ganz am Ende das aktuelle Bildschirmbild des Terminals, sodass auch eine Eingabeaufforderung ohne abschließenden Zeilenumbruch bereits darin sichtbar ist. Das Log wird als Klartext gespeichert, nachdem die Cursorbewegungen des Terminals ausgewertet wurden: Ein Fortschrittsbalken, der dieselbe Zeile immer wieder überschreibt, bleibt eine einzige Zeile, und eine in eine Abfragezeile getippte Antwort ersetzt diese Zeile, statt sie zu vervielfachen.

Der erste Bericht, den der Agent von einem Hintergrundbefehl erhält, beginnt ganz am Anfang des Logs – selbst wenn ein Teil davon schon zuvor im Vordergrund zu sehen war; spätere Berichte liefern nur noch neue oder geänderte Ausgaben nach. Nennen Bericht und Benachrichtigung nur den Prozess und sein Log, gab es seitdem keine neue Ausgabe. Bevor Rune meldet, dass ein Befehl auf eine Eingabe wartet, schreibt es das Log fest auf die Festplatte, damit auch ein neu gestartetes Rune den Stand ohne die alte Unterhaltung lesen kann. Gegen einen Festplattenfehler oder einen Absturz mitten im Schreibvorgang kann dies natürlich nicht schützen.

Tastatureingaben senden

Das Werkzeug process_control sendet Texteingaben an einen bekannten Hintergrundprozess oder beendet ihn samt allen von ihm gestarteten Unterprozessen. Es wartet weder auf das Prozessende noch gibt es die nächste Ausgabe direkt zurück. Die Sendeoption kann automatisch Enter anhängen, Enter erzwingen oder nur den reinen Text tippen. Ein leerer Text mit aktiviertem Enter sendet lediglich einen Druck auf die Eingabetaste.

Die Erkennung wartender Eingaben hängt von der Plattform ab: Linux erkennt jedes Warten auf Tastatureingaben, macOS erkennt nur verdeckte Eingaben wie Passwortabfragen, und Windows meldet solche Wartezustände nicht. Auf den beiden letztgenannten Systemen kann ein stiller Prozess also durchaus auf eine Eingabe warten. Rate niemals ein Passwort und bestätige keine potenziell destruktive Abfrage auf Verdacht, nur weil ein Prozess gerade nichts ausgibt.

Ausgabelimits und Lebensdauer

Das Standardlimit ab Werk für den an das Modell zurückgegebenen Text liegt bei 30.000 Zeichen. Davon getrennte Erfassungslimits betragen 8 MiB für Vordergrundausgaben und 100 MiB pro Hintergrund-Log; wird eines dieser Erfassungslimits überschritten, wird der Befehl gestoppt. Die vierzeilige Vorschau im Protokoll ist dagegen nur eine optische Einklappung.

Das Schließen des letzten Rune-Fensters beendet die aktive KI-Arbeit. Hintergrundprozesse können während der Haltezeit für getrennte Sitzungen (standardmäßig 60 Sekunden) weiterlaufen und werden danach beendet. Nutze einen regulären Systemdienst deines Betriebssystems, wenn ein Prozess dauerhaft und unabhängig weiterlaufen soll; verlasse dich nicht darauf, dass ein Hintergrundprozess von Rune unbegrenzt überlebt.
