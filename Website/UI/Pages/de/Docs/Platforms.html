Unterstützung im Überblick

Rune ist ein einziges Programm mit denselben Modi, Werkzeugen, Einstellungen und Daten auf jedem System. Die Unterschiede ergeben sich daraus, was das jeweilige Betriebssystem einem Programm erlaubt: wie eine laufende Programmdatei aktualisiert wird, wie Befehle isoliert werden und ob das System erkennt, wenn ein Befehl auf eine Tastatureingabe wartet. Linux ist die Hauptplattform. macOS und Windows befinden sich in der Beta-Phase: auf echten Rechnern gebaut und getestet, aber bisher mit weniger Alltagseinsatz im Rücken.

Für welche Systeme im aktuellen Release ein signierter Build vorliegt, steht direkt unter jedem Installationsbefehl auf der Startseite.

Linux

Befehle werden durch die Kernel-eigene Sandbox isoliert, sofern der Kernel diese bereitstellt – was bei den meisten aktuellen Distributions-Kernels der Fall ist. Fehlt diese Unterstützung, etwa auf einem älteren Kernel, weist Rune darauf hin: Im Modus Auto fragt dann jeder Befehl vorab um Erlaubnis, während Full ohne Rückfrage ausführt. /help zeigt unter This machine an, ob die Sandbox aktiv ist und welche Ausnahmen gelten.

Das Kopieren von Text läuft über dein Terminal, das Programmen den Schreibzugriff auf die Zwischenablage erlauben muss. Über SSH oder innerhalb von tmux bzw. screen ist diese Berechtigung mitunter deaktiviert; schalte sie im Terminal bzw. Multiplexer frei oder halte beim Ziehen Shift gedrückt, um die native Auswahl des Terminals zu nutzen. Zum Öffnen von Links im Browser wird xdg-open benötigt, das auf Desktop-Systemen standardmäßig vorhanden ist.

Auf Systemen, die ihre Programme in einem schreibgeschützten Paketspeicher ablegen – wie NixOS oder Guix –, dürfen Befehle lesen und ausführen, was in diesem Speicher liegt.

macOS

Befehle laufen in der macOS-eigenen Sandbox und sind auf dieselben Verzeichnisse beschränkt wie unter Linux. Beim Kopieren von Text wird direkt die System-Zwischenablage beschrieben; das Kopieren funktioniert daher auch im Standard-Terminal von macOS, das Zwischenablage-Anfragen über Terminal-Steuersequenzen ignoriert.

macOS meldet Rune nur verdeckte Eingabeaufforderungen wie etwa Passwortabfragen. Ein Hintergrundbefehl, der still auf eine normale Texteingabe wartet, sieht daher so aus, als würde er noch arbeiten; lies vor einer Entscheidung sein Protokoll und gib niemals auf Verdacht ein Passwort oder eine Bestätigung ein, nur weil ein Befehl keine Ausgabe mehr liefert.

Befehle werden in bash ausgeführt (das unter macOS vorinstalliert ist) und nicht zwingend in der interaktiven Login-Shell deines Terminals (unter macOS standardmäßig zsh). Über einen absoluten Pfad in terminal.shell kannst du eine andere installierte Shell festlegen.

Installiere Rune mit dem Befehl auf der Startseite. Eine im Browser heruntergeladene Kopie wird von macOS als Internet-Download markiert und von Gatekeeper blockiert, bis die Markierung entfernt wurde; Installieren & aktualisieren zeigt, wie das geht.

Windows

Rune isoliert Befehle über ein eigenes separates lokales Benutzerkonto. Beim ersten Start bittet Rune einmalig um eine Administratorbestätigung, um dieses Konto einzurichten. Lehnst du ab, fragt Rune nicht bei jedem Start erneut; mit rune -sandbox setup kannst du die Einrichtung jederzeit nachholen und mit rune -sandbox reset das Konto samt allen auf deinen Ordnern eingerichteten Zugriffsrechten wieder entfernen. rune -sandbox listet diese Zugriffsrechte auf und zeigt an, welche Isolierungsmethode aktiv ist.

Ohne dieses separate Konto isoliert Rune Befehle über ein eingeschränktes Token deines eigenen Benutzerkontos, wobei folgende Grenzen gelten:

  • Ein Befehl kann weiterhin alles lesen, was Windows jedem angemeldeten Benutzer zum Lesen freigibt – etwa Ordner direkt im Wurzelverzeichnis eines Laufwerks, andere Laufwerke und ProgramData – und kann in ProgramData auch Dateien anlegen. Dein eigener Benutzerprofilordner bleibt jedoch außerhalb seiner Reichweite.
  • Ein Befehl kann eine Named Pipe, die ein anderes Programm mit den Windows-Standardrechten erstellt hat, lesend öffnen. Schreibzugriffe auf eine solche Pipe werden verweigert.
  • Git Bash und andere MSYS2- oder Cygwin-Programme fragen vor jedem Befehl um Erlaubnis und führen diesen Aufruf anschließend mit vollem Zugriff aus. Die Windows-eigene HTTPS-Implementierung (genutzt von curl.exe und Invoke-WebRequest) schlägt innerhalb dieses eingeschränkten Tokens fehl; das eigene HTTPS von Git funktioniert hingegen weiterhin.

Ist das separate Sandbox-Konto eingerichtet, funktionieren sowohl Git Bash als auch das Windows-eigene HTTPS innerhalb isolierter Befehle. Rune gewährt diesem Konto keinen Zugriff auf die Systemordner von Windows, auf das Wurzelverzeichnis eines Laufwerks oder auf den übergeordneten Ordner aller Benutzerprofile; öffnest du ein Projekt direkt an einem dieser Orte, fragt jeder Befehl in den Modi Ask und Auto vorab nach.

Windows meldet Rune nicht, wenn ein Befehl auf eine Tastatureingabe wartet. Ein stiller Hintergrundbefehl wartet möglicherweise auf eine Eingabe oder arbeitet noch: Prüfe sein Protokoll, bevor du eine Eingabe sendest. Da eine laufende Programmdatei unter Windows nicht im Betrieb ersetzt werden kann, greift ein Update erst beim nächsten geöffneten Rune-Fenster, nicht in bereits offenen Fenstern.

Terminals

Tastenkombinationen und Mausgesten erreichen Rune nur, wenn das Terminal sie weitergibt. Konsole zoomt bei Ctrl+Mausrad, sofern das Profil nicht angepasst wurde, und manche Terminals wandeln Alt+Mausrad in horizontales Scrollen um; das einfache Mausrad und die Pfeiltasten funktionieren immer. Weiches Scrollen mit dem Mausrad wird nur in Terminals genutzt, die komplette Frames am Stück schnell genug neu zeichnen; andernfalls springt die Ansicht pro Raststufe direkt. Farben, Transparenz und Schriftarten werden vom Terminal gesteuert. Mit /help siehst du jederzeit, welche Eingaben dein installierter Build unterstützt.
