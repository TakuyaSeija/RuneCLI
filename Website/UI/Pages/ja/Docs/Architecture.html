ローカルエンジンとターミナルフロントエンドの分離

Rune はインターフェースとローカルのエージェントエンジンを分離しています。ターミナルフロントエンドはユーザーのコマンド送信とイベント描画を担当し、エンジンはタスク実行、プロバイダへのリクエスト、権限管理、セッション状態、およびファイル保護を担います。これにより、複数のウィンドウから同じセッションを閲覧している場合でも、常に一貫した判断基準が維持されます。

プロバイダはモデルの推論結果を提供するだけであり、ローカル環境での実行権限を持つわけではありません。モデルの出力はあくまで「提案」であり、他の処理と同様にツールの検証と実行制御を通過する必要があります。

リクエストの処理サイクル

  1. ユーザーが作業内容と明示的な添付ファイルを送信します。
  2. エンジンが関連するコンテキストを整え、選択されたモデルアカウントへリクエストを送信します。
  3. モデルがテキストまたはツール呼び出しの提案を返します。
  4. Rune が各呼び出しを検証し、現在の権限モード、アクセス境界、および該当するポリシー審査の判断を適用します。
  5. ツールの実行結果が記録され、次のモデルステップのコンテキストとして渡されます。
  6. フロントエンドに進捗、失敗、最終回答が表示され、ユーザーが実際の結果を確認します。

再試行、出力上限、キャンセル処理はランタイム側が管理します。モデルが「承認を通過した」とテキストに出力しても、自ら権限を付与することはできません。補助ジョブは、それぞれ固有の目的と上限を持つ個別のプロバイダリクエストとして実行されます。

セッションと実行順序

1 つのセッションには、唯一となる正規の作業ストリームが存在します。追加で開いたウィンドウはそれぞれ独立したコピーを実行するのではなく、同じタスク、質問、コスト集計、ファイル状態を共有して表示します。新しいメッセージや追加指示は順番に受け付けられ、すでに送信済みのプロバイダリクエストは送信時点のコンテキストを維持します。

会話履歴は実際に行われた処理の記録として保持され、後から変更した設定やファイル内容が最初から存在していたかのように書き換えられることはありません。コンパクションはモデルに渡すコンテキスト用の要約を作成するものであり、保存された履歴そのものとは区別されます。

ツールとプラットフォーム境界

組み込みのファイル、ターミナル、Web ツールは、明示的な入力と上限付きの出力を持ち、エンジン内の単一の実行経路を通ります。ファイルを変更する際は、対象ファイルの変更前の内容が保護されてから置き換えが行われます。コマンド実行には OS 固有の隔離機構（利用可能な場合）が使われ、共通の権限ルールとプラットフォーム上の制限は隠さず明示されます。

外部の MCP ツールは、宣言されたインターフェースを通じて検出・呼び出しが行われます。スキルは手順ガイドとして読み込まれますが、ガイドの内容や外部からのレスポンスがユーザーの承認に取って代わることはありません。ネットワークの送信先や認証情報は、モデルが扱うテキストとは分離して管理されます。

設定とアップグレード

グローバル設定にはユーザーが選択した値のみが記録され、既定値はアプリケーションのバージョン側に属します。実行中のプロセスは、各設定項目の反映タイミングに従って変更を取り込みます。既存のセッションでの選択や実行中のリクエストが、新しい既定値によって無条件に上書きされることはありません。

保存データの構造変更は、順序立てられたアップグレード処理として行われます。オプションのヘルプや利用できない認証情報ストアが、正常なアクセスを装ったり無関係なデータを破損させたりすることはありません。新しいリリースへの引き継ぎはセッションが安全な待機状態になるのを待って行われるため、インストールのために実行中の作業を強制終了する必要はありません。

設計上の境界と結果の保証

アーキテクチャによって「どこで実行可否を判断し、どう結果を報告するか」は強制できますが、モデルの計画が正しいこと、すべての外部システムが元に戻せること、あるいは許可されたコマンドが無害であることまでは証明できません。差分の確認、テストの実行、最小権限でのタスク設定、および個別のバックアップは引き続き不可欠です。
