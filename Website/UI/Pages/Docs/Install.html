What you need

Linux
x86_64 or arm64, wherever a signed build for that processor is published. Each release says which builds it has. The glibc build runs on distributions with glibc 2.17 or newer, and was run on CentOS 7, Debian 11 and 12 and Ubuntu 24.04. The static musl build needs no C library of the system, and was run on Alpine.
macOS
macOS 11 or later, on Apple silicon or Intel. macOS support is in beta.
Windows
Windows 10 version 1809 or later, or Windows 11, on x64 or ARM64. Windows support is in beta.
The installer
On Linux and macOS: curl, tar, gzip and openssl (OpenSSL or the LibreSSL that macOS ships) for the signature check. On Windows: PowerShell, which every supported Windows has. On Linux and macOS run it as your normal user, not root; on Windows it needs no Administrator rights.
A model account
An account with a provider you choose, or a model service on your own computer. See Model providers.

Which of these systems has a signed build in the current release is stated under each install command on the home page. Differences between the systems are in Platform support.

Install

The install commands are on the home page: install.sh for Linux and macOS, run by sh, and install.ps1 for Windows, run in PowerShell. Read the script first if you like: both are served as plain text, install.sh and install.ps1, exactly as the command receives them. Each runs these steps and stops at the first one that fails, with nothing changed:

  1. Checks the system and its version, that it runs as a normal user, and that its tools are present.
  2. Detects the processor, and on Linux the C library, glibc or musl.
  3. Downloads the release's checksum list and verifies its signature with the release key written into the script.
  4. Downloads the archive for your machine and checks it against that signed list.
  5. Checks that the archive holds only the program and its license files, and that the program starts and reports the expected version.
  6. Puts the program in place in one rename, and the license and third-party notices beside your other user data.
SystemProgramLicense notices
Linux, macOS~/.local/bin/rune~/.local/share/runeagent (or $XDG_DATA_HOME/runeagent)
Windows%USERPROFILE%\.local\bin\rune.exe%LOCALAPPDATA%\RuneAgent

It never edits your shell profile or your PATH. If the folder is not on your PATH, it says so. Release verification explains what the signature does and does not prove, and how to check a download by hand.

The install commands download with curl and PowerShell, which do not mark the program as coming from the internet. An archive you download in a browser is marked. On macOS, Gatekeeper then refuses to start that copy of rune; after verifying the archive, remove the mark with xattr -d com.apple.quarantine rune. On Windows, SmartScreen can warn when such a program is opened from File Explorer.

Installer options

Unset, the installer takes the newest published version, your user bin folder and, on Linux, the detected C library. On Linux and macOS, save the script as install.sh, read it, then run it with any of these variables. On Windows, set them in the same PowerShell window before running the command.

RUNE_VERSION
A published version such as {{.DocVersion}}. Older versions install by number.
RUNE_INSTALL_DIR
An absolute folder for the program instead of the default.
RUNE_LIBC
Linux only: gnu or musl, to choose the build instead of detecting it. A combination with no published archive is refused.
RUNE_VERSION={{.DocVersion}} sh install.sh
RUNE_INSTALL_DIR="$HOME/bin" sh install.sh
$env:RUNE_VERSION = "{{.DocVersion}}"
irm {{.Origin}}{{url "install.ps1"}} | iex

Put rune on your PATH

Many Linux distributions already include ~/.local/bin, but only once the folder exists when you log in; macOS does not. If rune is not found, add the folder yourself. For bash or zsh, the default shell on macOS, add this line to ~/.bashrc or ~/.zshrc, then open a new terminal:

export PATH="$HOME/.local/bin:$PATH"

In fish, run fish_add_path ~/.local/bin once. On Windows, this PowerShell line adds the folder to your own PATH; open a new terminal afterwards:

[Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path", "User") + ";$HOME\.local\bin", "User")

Use your own folder if you set RUNE_INSTALL_DIR.

The first start

Open a terminal in your project and run rune. On its first start Rune creates its data folder, .rune in your home folder (%USERPROFILE%\.rune on Windows), or the folder named by RUNE_HOME. It holds:

  • rune.toml, your settings. It records only the choices you made; every other value comes from the version you run.
  • Your API keys, encrypted.
  • Sessions, project memory and the snapshots that undo uses, kept per project.

On Windows the first start also asks once for Administrator confirmation to set up the separate account Rune runs commands in. If you decline, Rune does not ask at every start; run rune -sandbox setup when you want it. Security explains what changes without it.

rune -config prints the folder in use on its first line. Rune keeps its own data there, not in your projects: a project changes only through the AI's tools under the mode you choose, your own ! commands, or a skill or MCP change you save with project scope. Continue with connecting a model in the Introduction.

Update

Run the installer again for the version you want, with the same RUNE_INSTALL_DIR if you set one. It verifies the download and replaces the program in one step; check the result with rune -version.

Rune windows already open keep working. On Linux and macOS they move to the new build by themselves once they are idle, and the first start of a new version updates your data folder for it. On Windows a running program cannot become another one: open windows keep the version they started with, and the next Rune you open uses the new one. Do not close active work to force this.

Uninstall

Finish or stop your work and close every Rune window. Then remove the program and its notices. On Linux and macOS:

rm ~/.local/bin/rune
rm -r ~/.local/share/runeagent

On Windows, in PowerShell:

rune -sandbox reset
Remove-Item "$HOME\.local\bin\rune.exe"
Remove-Item -Recurse "$env:LOCALAPPDATA\RuneAgent"

On Windows, rune -sandbox reset first takes back the access Rune's command sandbox was given on your folders and removes its account; it may ask for Administrator confirmation. Your data folder stays until you delete it yourself. It holds your history, settings, keys and restore points, and is not needed to uninstall. If you do delete it, read its location with rune -config first, and never remove it while Rune is still running.

Environment variables

RUNE_HOME
Use another data folder instead of .rune in your home folder: its own settings, keys and sessions.
NO_COLOR
Print without colour, as --no-color does.
RUNE_THEME
Tell Rune your terminal's background when the terminal does not report it: dark, light or a hex colour. It is not the theme choice, which is in Appearance.
RUNE_VERSION, RUNE_INSTALL_DIR, RUNE_LIBC
Read only by the installer; see Installer options.
